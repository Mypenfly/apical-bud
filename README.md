# apical-bud（顶芽）

[English](README.en.md) | 中文

**开发前的需求推演方法论**：从一句可能模糊的需求（种子）出发，先把里面说不清就没法动手的词**拆开、由你逐项认领**（根系），再推演**两跳**——第一跳把需求说定（**需求定稿**），第二跳定出**唯一一个理念概念**（顶芽），然后写"靠什么保证"（侧枝），理念定稿之后再据判据推出技术方案（果实）。**每一跳都是先摊开几条互不相容的候选，再由你挑。**

```
种子 ──► 根系 ──► 主干（两跳）──► 需求定稿 ──► 顶芽 ──► 侧枝 ──► 果实
需求     拆词认领   候选 ⇄ 定论    一句你说"就是这个"的话  理念概念  机制+延伸  技术方案
```

**为什么要有"需求定稿"这一跳**：跳过它直接谈理念，谈的就是我知识库里的现成方案，不是你的需求。第一跳的验收标准只有一条——**你能指着那句话（`concept/need.md`）说"对，我要的就是这个"**。这也正是这套方法存在的理由：让你更清楚自己最初那句模糊的话到底在要什么。

**气质在顶芽，保证在侧枝**：顶芽回答"这一屏是什么气质"（可解释、能生成，不要求可证伪）；`M-` 机制命题回答"靠什么保证"（可证伪、带反例），它们是技术选型的限制条件——判据的 `来源:` 里必须有 `M-`，否则选型就退化成"市面上有什么"的盘点。

调研是**肥料**：供给前提与佐证，不代替生长。问答是**生命力**：树每长一节，都要经过一轮问答。全程文件驱动——没有落盘的决定不算决定。

它是一个 skill（`SKILL.md` + `references/` + `templates/` + `scripts/`），也是一个 DSH agent preset（`apical-bud`）的方法论内核。八条不常见的主张：

1. **对话是介质，文件是留痕。** 提案、候选、推演链都先说在对话里——你不必打开任何文件就能回答；文件只记录已经发生的事。讨论一旦退化成「它写、我读、我挑错」，就是因为这条被违反（DSH preset 里有写守卫兜底）。
2. **推演，不是灵感；但候选可以先没有论证。** 每个 `kind: 定论` 的节点都必须写清它从哪个父节点推出来，祖先链必须能走到种子。`kind: 候选` 不查这条——摊候选时本来就还没有论证，那正是它叫候选的原因。凭空冒出来的东西，两条都不算。
3. **没有候选就没有挑选。** 每个要定下来的项，先摊开至少两条**互相对立**的候选（`## 对立面` 要互指），每条写清"选了它要放弃什么"。一条找不到对立面的"候选"，其实是结论。
4. **层从你的话里来。** 种子里的词由我拆成项、**由你逐项认领**（核心/次要/不算）。我自己切的角度写在层文件的「其他解读（被否）」里，不冒充你的需求。
5. **顶芽只有一个，机制可以有好几个，剪掉的枝留着。** 理念概念唯一；机制命题允许竞争、允许复活。淘汰要写成有条件的判断（淘汰理由 + **复活条件**），并在进入 S3/S5/S6/S7 之前**全量重判**一次——淘汰是当时的推断，推断变了结论就作废。
6. **你写自己的答案时，我不顺着走。** 答复先判落点（选项内 / 改写我的选项 / **选项外的新内容** / 只是重申 / 与树上冲突），再跟已经定下的层与节点比一遍；冲突就当场提异议。落在选项外时，我必须先回答"我的选项集错在哪"。
7. **实验由你执行，但"要不要做"由我判断。** 依赖"某个程序到底怎么表现"的推演，先读源码（写不出出处就是没读）；真机实测交给你时，给**交接文档 + 一段可直接复制的提示词 + 通过/不通过标准**。读一次源码能得到答案的，不许让你重启机器。
8. **术语不能堆成墙。** 一轮最多引入一个新词，未确认的词同时最多一个，定义必须是人话且不能用未定义的词解释自己；**字段名和标题也算术语**，新增之前先问你怎么叫，也不拿新比喻去命名机制。**你可以改写任何问题与术语，也可以反悔任何已定的东西**（不需要理由），我负责全局替换、记下曾用名，并把旧内容标成被取代（不删除）。

## 安装

**DSH（DeepSeek Harness）**：

```bash
git clone git@github.com:Mypenfly/apical-bud.git ~/.dsh/skills/apical-bud

# 可选：装上会话装配层（常驻身份、写守卫、apical_gate 工具、状态横幅）
~/.dsh/skills/apical-bud/dsh-preset/install.sh
```

`dsh-preset/` 里的预设会把三条承重规则变成机制：`write`/`edit` 只能写讨论根、用户原话与既有轮次纪要只追加、`state.json.stage` 只能由 `apical_gate` 在出口条件通过后推进。只装 skill 也能用：模型会在需要时加载它，或你用 `/apical-bud` 手动调用。细节见 [`dsh-preset/README.md`](dsh-preset/README.md)。

改完 skill 或 preset 之后记得跑一次 `install.sh`，并**新开一个会话**：persona 与 SKILL.md 在会话开始时就注入了，已经在跑的会话不会中途换规矩。

**Claude Code / 其他兼容 SKILL.md 的宿主**：

```bash
git clone git@github.com:Mypenfly/apical-bud.git ~/.claude/skills/apical-bud
```

门禁脚本是零依赖 Node ESM，任何宿主里都能跑：

```bash
node scripts/gate.mjs --root design/<slug>
```

## 用法

说"我们聊聊这个想法""帮我理清需求""这个概念该怎么设计""这个方向值得做吗"，或直接 `/apical-bud`。讨论会在你的仓库顶层建 `design/<slug>/`：

```
seed/          种子：原话 + 一句话真实需求 + 被否的表述 + 非目标 + 判定对齐的信号 + 拆词与认领
layers/        根系：层（L-00N）——种子某个词的一项，由你认领为"核心"
derivation/    主干：推演节点（N-00N），kind: 候选（带对立面）/ 定论（带推演与反例）；淘汰的枝保留
concept/       need.md ★（需求定稿，第一跳的落点）+ concept.md ★（顶芽）+ extensions.md ★（侧枝 M-/E-）
tech/          果实：criteria.md（先锁版）→ options.md → selection.md ★
questions/     待决问题（Q-00N）        decisions/  决策记录（D-00N）
glossary.md    术语表（[确认] / [提案]）  audit/      异议、裁决、全量重判、门禁日志
```

**一个项目可以有多棵树。** 不同需求、不同阶段各一棵，树与树之间还能声明关联（`state.json` 的 `dependsOn` / `relation`，正文里用 `<slug>#L-003` 互相引用）。一个会话绑定一棵树：

```bash
apical_gate action=trees                 # 列出项目里的全部树与生命周期状态
apical_gate action=bind slug=<slug>      # 绑定本会话要推进的那一棵
```

一棵树走完 S7（或裁决终止）之后不要在它上面长新需求——新建一棵树，并在种子里写「与已有树的关系」：继承了什么、推翻了什么。

完整的目录、ID、frontmatter 与门禁契约见 `references/doc-conventions.md`。

## 门禁

```bash
node scripts/gate.mjs --root design/<slug>            # 人类可读报告
node scripts/gate.mjs --root design/<slug> --json      # 机器可读
node scripts/gate.mjs --cwd .                          # 自动发现唯一的讨论根
node scripts/gate.mjs --root design/<slug> --stage S5  # 用别的阶段视角检查
```

退出码 0 = 通过，1 = 有缺失项。它同时是模块，宿主插件可以 `import { validate } from './scripts/gate.mjs'` 直接调用。

它检查的是**结构与可追溯性**：定论节点无孤儿、候选有互指的对立面、层有用户认领与判据、拆词与认领真的发生过、需求定稿覆盖第一跳的每条定论、顶芽一句话 ≤60 字、关键名词都是已确认术语、推演链从种子经 `need` 到顶芽逐跳不断且覆盖每一个保留的定论、机制命题带 `服务:` 与反例、判据先于方案锁定且至少一条来源指向 `M-`、候选方案挂在保留的节点或机制上、进 S3/S5/S6/S7 之前有全量重判记录。它**保证不了理念好不好**——那是红队复核和你自己的判断。

## 出处与许可

提问纪律（一次一问、给具体选项、能从文件查到的不问人）改编自 [grill-me](https://github.com/RobMitt/grill-me-skill) 的思路；在其上补了四件它没有的东西：**推演树的可追溯性、拆词与认领、阶段门禁、以及质疑/否决权**。

**要说明一句**：grill-me 是审问**已经成形的方案**的工具，天生收敛。把它那套"我给选项、你挑一个"直接搬到"把一句模糊需求打开"上，会得到一个模型端菜、用户勾选的流程——用户没有产出内容，也就谈不上被启发。所以这一版把发散与收敛分开：**先摊开候选（这一步允许没有论证），再由用户挑**。

"答复落点判法"与"我正要写下这些句子时，删掉重写"这两张表，形态取自 [superpowers](https://github.com/obra/superpowers) 的合理化对照表与 `receiving-code-review`；"每个问题都要写出我的倾向"取自它的 brainstorming。它那边没有概念推导方法论，所以只借了行为塑形的手法。
