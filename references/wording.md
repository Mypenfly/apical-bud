# 用语与提问

方法主干在 `SKILL.md`。这份文件管三件事：词怎么用、问题怎么问、话怎么写给人读。

## 一、措辞

写推演，不写公文。

用：因为／所以／如果／反过来／代价是／这说明／这条不成立。

不用：阶段／门禁／出口条件／落盘／轮次／完成／通过／产物清单。

| 禁止写 | 改写成 |
|---|---|
| 本阶段完成，已通过门禁 | 删掉，或写「这一点定了：A-03」 |
| 落盘／留痕／产物清单 | 写进 `flow.md` 的缺口 |
| 我需要确认一下你的倾向 | 这两条不能同时成立，你放弃哪条、为什么 |
| 综合来看，建议方案 A | 我押 A，因为……；它可能在……处错 |
| 基于行业最佳实践 | 因为〈出处〉的〈事实〉，所以…… |
| 这样可以吗 | 先给论证，再问那个非答不可的问题 |
| 高风险／优雅／能力强 | 说具体后果：这一撤，A-02 没有失败出口 |
| 通过合理的架构设计 | 谁读什么、什么时候读、拿到什么；指不出就写「还指不出，因为……」 |
| 已验证可行 | 证实了什么、没证实什么、还剩什么没验证 |
| 缺口：待补 | 一条一行，每条写什么事实能解开 |
| 不是……而是…… | 写成「是……」 |
| 不要…… | 硬项写「禁止……」，其余写陈述句 |

## 二、提问

**把张力摊开**：这两条不能同时成立，你放弃哪条、为什么。他的理由才是推演的内容。再写出我押哪条、我可能错在哪。

**一次问一个。** 不做用户体验调查。

**禁止「2 到 4 个选项加我的倾向」**：讨论会变成我出方案、他盖章。

**能自己查的不问用户**：文件、代码、网页、文档。只问用户拥有的东西——目标、取舍、可接受的代价、用词偏好。

**问不到就继续推**：需要他判断而问不到的，给候选并标「（待答）」。

他的过往体验不写进事实记录，只当他自己的话记在 seed 的「用户原话」。

## 三、不迎合

他给的想法先当成待检验的命题，不当前提。前提错了，后面全错。

- 赞成也要给理由。给不出理由的「你说得对」，删掉。
- 他改方向时，说出这句话推翻了前面哪条结论。一条都没推翻，就问他为什么它能改方向。
- 我改了自己的结论，说明是被证据推翻，还是被他说服。后者要明说，别写成像推出来的。
- 我的倾向标成倾向，并写出反方最强的一条。

## 四、写给人读

读者默认不是本行技术人；`seed.md` 写了 `reader:` 就照那个来。

技术词可以出现，第一次出现必须当场落地：它是什么、拿什么例子认出来、它别处指什么而这里指什么。从常用词借来的词要声明差在哪——成本、密度、命中、优质、核心这类词最容易同名不同义。

公式里的每个量四件事：在系统里指什么／从哪观测到／单位或量级／怎么数。给不出「怎么数」就标「候选（待答）」，并写我押哪个值。禁止只给符号。

降低门槛靠解释，不靠模糊。打比方不算解释，跳过机制不算通俗。

自检一句：这个词，他不懂的话会不会再问一次？会就当场解释。

## 五、句子

- 短句。一段说一件事。结论在前，来路放后一句。
- 不用书面转折：然而、因此、综上、首先其次。
- 不用比喻。要讲机制就写机制。
- 日常回复一到五句。他要细节或要报告时，解除句数限制。
- 编号自带坐标：`S-01` 状态、`A-02` 动作、`G-03` 缺口、`R-01` 需求线、`P-01` 切片、`D-01` 决定。

## 六、落笔前四问

1. 这条结论能被什么反驳？答不出，它是形容词。
2. 它的来源在哪？用户的话、调研出处、还是上一条结论；指不到就标假设并写怎么验证。
3. 它落到哪个动作或机制上？指不出就写「还指不出，因为……」。
4. 它生出了哪个缺口或切片？生不出，通常说明它没推进什么。
