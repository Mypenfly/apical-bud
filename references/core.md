# 核心、需求线与循环

方法主干见 `SKILL.md`。这份文件收三件事：怎么只留一个核心、推演的循环怎么转、两种"由前面得出"怎么标。

## 一、只留一个核心

用户一口气要的从来不止一样。**不选核心就往下拆，后面每一步都在给两个互相打架的目标打工**——推得越顺，实现阶段越收不了场。

| | 含义 | 数量 |
|---|---|---|
| **核心** | 他真正要换来的那一个东西。整棵树为它服务 | **恰好 1 个** |
| **检验条件** | 核心达成时不许破的底线 | 不限；超过 3 条提醒他"要的太多" |
| **非目标／挂起** | 这次不做、不归这棵树管 | 进 `seed.md` 的非目标 |

「检验条件」有门槛，三关都过才算：**可检验**（什么情况算破了它本身）／**有代价**（破了会怎样）／**有归属**（谁说的）。三关缺一关，它是第二个核心目标假装的——**指出来，禁止默认收下**。

**代价要写出来**（`seed.md` 的「核心与放弃代价」）：我押哪条是核心、放弃了哪条、放弃会失去什么、我可能错在哪。**用户为什么肯放弃那一条，比他要了什么更有用**——那才是推演的内容。

用户不肯选，把两条都标候选、写清"这两条不能同时成立，选哪条由你定"，然后**按其中一条先推**（写明我押哪条、错在哪）。推演出来的分歧比追问更快让他做选择。

## 二、推演的循环

```
用户需求
 → 先选核心          成本与效果不能同时全额买到 → 用户选成本，效果降为检验条件
 → 拆词              成本在哪、怎么算？效果受什么影响？
 → 逐项论证          成本＝命中输入＋未命中输入＋输出，前两者是总量的大头；
                     效果的影响项里，模型参数量不归本树管，内容质量与内容位置归
 → 一个节点走一遍     命名（信息密度）→ 组成 → 为什么 → 怎么落机制 → 生出新概念／新问题
 → 倒回去解释        优质 token / 劣质 token；compact 之后为什么糊涂
 → 长出新结论与未定项  引入副模型；但"谁来判断、何时介入"还没定 → 下一个节点谈它
 → 再一个节点 ……     未定项被解决、且没有长出新的
 → 未定项清零 → 概念自洽且可实现 → 概念模型 → 技术选型（实验可推翻它）→ 交接件与实验文件
```

**每一步的内容都由前面已经写下的东西得出，最前面的东西是用户的需求。** 凭空来的东西——刚查到的事实、刚想到的说法——是材料，进 `facts.md` 与 `## 已知`；出发点永远是前面已经写下的那一句。

## 三、五问：一个节点走一遍

**五问是一种展开方式，形式随你。** 按 `what / parts / explain / how / new` 分节写可以，按「问题／已知／推论／结论／怎么落机制／反过来／生出的问题」写也可以。**禁止跳过任何一问**——实测里最常被跳过的是 `how`（怎么落机制）和"解释不通的地方"。

| 问 | 要回答什么 | 最常犯的错 |
|---|---|---|
| **what 命名** | 这一步在谈哪个词，它是什么 | 谈了三段还没给这个词命名；或者名字是形容词串 |
| **parts 组成** | 它由什么组成，落到子项一级 | 只给一层，子项没点名回答就过去 |
| **explain 为什么** | 为什么是这几块；旧的为什么不行 | 只描述不论证——"它包含 A 和 B"不论证任何事 |
| **how 怎么落机制** | 谁读什么、何时读、拿到什么、什么算失败 | 写成"通过合理的架构设计"；或者干脆没写这一节 |
| **new 新概念／新问题** | 长出了哪个新词，或哪个问题还没答 | 生不出问题却当已经收敛；或生出一堆问题却不认领 |

### 命名：把几项论证合成一个词

把几项论证合到一起看，得出一个能同时罩住它们的词。它必须**能算**或者至少**能判**，否则它只是好听。

- "成本和效果在 agent 领域里一体两面" → **上下文中的有效信息密度**。
- 定义落地：密度 = 起引导作用的 token ÷ 全部 token。

**这一步的产物是一个概念。** 一个概念顶得上一串"因为…所以…"。

### 组成与论证：一项一项回答掉，调研在这里

拆出来的每一项都要**有依据地**回答，答案来自外部事实：官方文档、源码、论文、账单、实测输出。这一步得出两样东西：

1. **材料**：这一项由哪几块组成，哪几块是大头。
   - 成本＝缓存命中输入＋未命中输入＋输出，前两者是总量的大头。
   - 效果的影响项：上下文内容质量、内容在上下文里的位置（开头与结尾权重最高，与注意力机制有关）。
2. **范围**：哪一项不归本树管，在这里排除掉，并说清为什么。
   - 模型参数量（"模型多大"）不归 agent 系统开发管——它是选型输入，本树动不了它。

**排除是这一步最重要的产物之一。** 不排除，后面每一步都会拖着不属于这棵树的东西走。

**论证要到子项一级。** 一条线里常常含着好几项（"坐标：维度、原点、度量"），每一项都要点名回答掉；答不了的标「（待答）」。整条线答一半就过去，后面每一步都建在没答的那半上——而且没人看得出来。

### 解释：拿这个概念解释需求与刚才拆出来的每一项

新概念要能解释你已经拆出来、论证过的东西，解释不通就换词。这是循环里最容易跳过的一步，也是唯一能当场验证概念的一步。

- 用密度解释现象：传统 harness 是"纯增长 + 用户自行 compact"；compact 之后优质 token 的**比例**上升、**总量**下降——所以模型在 compact 之后有一段糊涂。
- 再把论证过的成本三项重挂一遍：它们逐条对应到"劣质 token 占计价 / 劣质 token 干扰输出并继续变成劣质 token / 每次重开 session 重新取样"。

**解释不通的地方就是问题所在地**，它生出下一步。

### 落机制：写清谁读什么、什么时候读

一个概念说到"它是信息密度"，还没法让人动手。**指到具体机制或接口**：谁读什么、什么时候读、拿到什么、什么算失败。

- 密度这块指到机制上就是：判断只读异常点附近的片段；在错误将要固化时注入；注入的内容必须带出处。

**指不出来就写"还指不出，因为……"**——那是一条更诚实的结论，它本身就是下一个节点的入口。

### 生出新概念与新问题

推演不停在"解释得通、指得到"。过程中会浮出一个新结论，新结论又逼出新问题。

- 从"劣质 token 识别不了、优质 token 认得出来"这个**不对称**，得出：提高效果的方向是**注入**——过滤这条路的门槛是先认出劣质 token，而这一步谁也做不到。
- 顺着问：谁来判断、判断什么、什么时候判断 → 于是**引入副模型**，接过人在"修正 / 引导"里的角色。
- 再问：它要哪些信息？何时介入？介入多深？它自己的上下文怎么管？主副都满时怎么办？
- 推一条子问题撞上新矛盾（它要的信息比主模型还多）→ 试探解法（按信息模块拆）→ 又生两个新问题（怎么切、并发与成本怎么平衡）。
- 把此前假定不会发生的因素提出来（信息时效性）→ 推出后果：优质 token 会劣化，而它一旦劣化，依赖它的一切跟着变劣质。

**每个结论都要能生出问题。** 生不出问题的概念，要么已经自洽（可以收敛），要么是死路（写出来，标 `closed`）。

## 四、两种"由前面得出"要分开写

混在一起就分不清这一步在答哪条线、由哪一步长出来：

| | 写在哪 | 意思 |
|---|---|---|
| `answers: [Q-03.2]` | 回答问题 | 这个节点在回答**哪一步生出的问题** |
| `from: [D-03.1]` | 拿结论当前提 | 这个节点由**哪些结论**长出来（只放 `D-`，不放 `F-`） |
| `line: R-02` | 服务需求线 | 这个节点服务**哪条需求线**（核心或一条检验条件） |

`line:` 是服务关系，`answers:`／`from:` 是来路关系。一条线可以有很多节点（`line:` 相同），但每个节点的来路必须指得出来。

**一个节点认一个词。** 想同时命名两个概念，就拆成两个节点——一个节点做两件事，读的人分不清这一步推进了什么。

## 五、需求线：拆的是需求自己的词

**名词问"由什么组成、怎么算"；形容词问"有哪些特征、怎么评价"。** 每一项写成一条线（`R-01`…），问的是一个**客观问题**——有外部答案，不取决于谁的感受。

- 「成本由哪几项组成」可以；「你现在哪里不满意」不行。
- **需求线只放需求里的词。** 推演中冒出来的问题进节点的「生出的问题」。
- **每条线都要被论证、都要有推演节点。** 写进种子的检验条件必须有人验，否则它只是写给人看的。
- **核心问题必须同时压住每一条线。** 压不住就明写「R-02 降级为……，理由……（待用户认领）」。
- 一条线连着吃掉四个节点，另一条一个都没有：树偏了，`map.md` 里直接看得见。
