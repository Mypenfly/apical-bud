# S6–S7：果实（技术方案）

> **落盘时机**：本阶段谈定的任何内容，都先在对话里说清楚、拿到你的答复，再写进文件。**提案不落盘**——文件是留痕，不是介质。

**前提：`concept/concept.md` 已经是 `status: final`。** 果实长在顶芽上：选型回答的是"用什么实现这个理念"，不是重新设计理念。如果选型过程中发现理念站不住，正确动作是回退 S5/S3 并记录原因，而不是用技术方案去补理念的洞。

## S6：先锁判据，再看方案

顺序是硬要求，门禁会检查 `criteria.md` 的 `locked_at` 早于 `options.md` 的 `created`。原因很朴素：先看方案再定判据，判据一定会被方案带偏。

### 判据只能从树上来

每条判据的 `来源:` 必须指向存在的 `R-000` / `L-00N` / `N-00N` / `M-00N`（门禁校验），并从下面这些位置推导：

| 来源 | 推出什么判据 |
|---|---|
| 种子 | 目标的硬性要求：必须在什么场景下做到什么 |
| 层 | 结构约束：哪些维度不能被牺牲 |
| 推演节点 | 机制约束：这个主张要求技术具备什么能力 |
| **机制命题 `M-00N`** | **选型的限制条件**：机制命题是概念在技术上的落地约束，每条判据至少要能挂到一条 `M-` 上（挂不上的判据，要说明它是谁的要求） |
| 调研事实 | 环境约束：平台限制、许可证、配额、既有系统 |

**候选从哪来，取决于判据，不取决于市面上有什么。** 若一份候选清单只是"本机仓库里能装到的东西"，它就不是选型，是盘点——把它降级为背景事实，回到 `M-` 重新问"这个机制需要技术具备什么能力"。

判据必须**可验证**：`K-001 单机可离线：不引入额外服务即可运行`，而不是 `K-001 简单`。`硬约束: 是` 的判据不满足就是淘汰，不参与加权。权重里掺入的**用户偏好**必须显式标明（"我就是想用 X 语言"），不要伪装成推导结果。

### 锁版

写完把 `status` 改为 `locked`、`locked_at` 填 `"YYYY-MM-DD HH:MM"`，然后才开始 `options.md`。锁定后要改判据，只能新增一份判据修订 + 一条决策记录，并写清原判据为什么不成立。

**反模式**：把"我熟悉""最流行""朋友推荐""AI 说它最好"写成判据。它们可以是偏好项，不能是判据。

## S7：候选、证据、定稿

### 候选要求

- ≥2 个真实候选 + **一个「什么都不做 / 最小方案」对照项**。如果最小方案其实满足硬约束，结论就应该是它——这常常是整场讨论里最省钱的发现。
- **`清单来源:`**（每个候选条目之外单列一行）：这份候选是从哪儿数的、我查了哪些、**没查哪些、因此可能漏什么**。禁止假穷尽："就这么几个"必须能被查证。
- **`体现:`**：这个候选体现概念的哪一句、满足哪条 `M-`。挂不上的候选不是选型结果，是调研肥料——放进"已考察未入册"一节，不要伪装成候选。
- 每个 `## O-00N` 写：`判定:`、`证据:`、`推演来源:`、满足/不满足哪些 `K-00N`、引入成本。
- `推演来源:` 必须指向存在的推演节点或机制命题（门禁校验）：每个方案都要说清它实现的是树上哪一个主张。**采纳/备选**项的来源必须是**保留**的节点/机制；**淘汰**项可以指向被剪掉的枝——那往往正是它出局的原因，写清楚反而更有价值。
- 淘汰者必须写 `拒绝理由:`，具体到判据与事实（"K-004 要求单机部署，它必须引入 Redis"），不写"生态一般""不够优雅"；并附一行 **`复活条件:`**（什么事实出现就该重新考虑它）。
- **候选是组合不是单品**：语言 + 框架 + 存储 + 部署 + 关键库之间存在锁定关系。选一整套并检查一致性。

### 证据分级

| 等级 | 含义 | 例子 |
|---|---|---|
| E1 | 官方文档 / 规范 / 源码 | 确认 API 存在、许可证是 MIT |
| E2 | 本人实测 | 跑通 quickstart、写 30 行原型、跑一次基准、验证一个关键假设 |
| E3 | 二手评价 | 博客、论坛、AI 转述、别人的经验 |

规则：关键判据（尤其硬约束）只靠 E1/E3 支撑的结论，必须在 `selection.md` 的 `## 未验证假设` 里逐条声明并写明验证时点。门禁要求至少一条 E2，或在"未验证假设"中明确写"无"。

E2 不需要写生产代码：原型放 `design/<slug>/tech/probes/`，注明是一次性取证产物。**本会话不能改机器**——要跑就得走三件套（见 `derivation.md`）：交接文档 + 可直接复制的提示词 + 通过/不通过标准。这一步不是实现，是花 30 分钟买掉一个风险。

### 定稿文档要求的五节

1. `## 选定方案`：完整技术组合，带版本或范围。
2. `## 判据对照`：每条判据一行，写"满足 / 部分满足 / 不满足 + 证据等级"。
3. `## 拒绝理由汇总`：表格：被拒方案 + 失败判据 + 证据等级。
4. `## 退出成本与迁移`：**半年后换掉它需要重写什么**；数据与接口的锁定程度；现在就该留的后路。
5. `## 未验证假设`：没有 E2 支撑的每条假设 + 风险 + 验证时点。

另加 `## 与顶芽的对应`：这套选型如何支撑核心概念与三档侧枝；不支撑的地方要明说（例如"猜测档延伸需要 X，本选型不预留，届时需重做 Y"）。

### S7 红队复核

与 S5 相同流程（见 `apical.md` 的提示词），关注点换成：

- 有没有一条硬约束其实不满足、只是被含糊带过？
- 有没有哪个"实测"其实只是跑通了 hello world？
- 被淘汰的候选里，有没有一个其实更好、只是淘汰理由写得太轻？
- 退出成本是否被低估（迁移数据、重写接口、团队学习）？

### 选型之后

讨论模式的任务到此结束。产出一份交接说明（`tech/handoff-<主题>.md`）：哪些决策必须先落地、哪些假设要最早验证、哪些接口要留后路，**外加一段可直接复制的提示词**（用户拿去在标准模式新会话里粘贴，自包含）。真正的实现交给标准模式的会话。

## S6/S7 出口条件（门禁摘录）

- S6：`criteria.md` locked、≥5 条判据、每条有权重/硬约束/合法来源（含 `M-00N`）、≥1 条硬约束；`options.md` 不早于锁版时间；**进 S6 前做过全量重判**（`audit/recheck-S6.md`）。
- S7：`selection.md` final 且五节非空；≥2 个候选，各带证据等级、`清单来源`、`体现`、与保留节点/机制的推演来源；淘汰者有拒绝理由与复活条件；≥1 条 E2 或"未验证假设"写明"无"；**进 S7 前做过全量重判**（`audit/recheck-S7.md`）。

## 全量重判（进 S6 / S7 之前）

写判据之前、定稿之前，各做一次：把 `status: dropped` 的节点、被淘汰的主张、候选里的淘汰项、`## 未验证假设` 逐条过一遍，结论写 `audit/recheck-S6.md` / `recheck-S7.md`。

- 每条要写**维持还是复活**，即使维持也要写一句为什么；
- 淘汰是**有条件的判断**：当时依据的推断/判据变了，它就作废；
- 确实该复活的，走反悔流程（新条目 `supersedes:`，旧的标 `superseded-by:`），不要偷偷改旧文档。
