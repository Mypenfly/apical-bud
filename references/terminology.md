# 用语

方法主干见 `SKILL.md`。**这一半和文件组织一样重要**：用词松了，推演会滑成汇报和形容词。

## 一、用哪些词

**写推演，禁止写公文。**

- 用：因为／所以／如果／反过来／这说明／代价是／这条不成立。
- 不用：阶段／门禁／出口条件／落盘／轮次／完成／通过／产物清单。

| 禁止写 | 改写成 |
|---|---|
| 本阶段完成 / 已通过门禁 | （删掉，或写"这一点结掉了：D-03.1"） |
| 落盘 / 留痕 / 产物清单 | 写进 `derivation/03-….md` |
| 我需要确认一下你的倾向 | 这两条不能同时成立，你放弃哪一条、为什么？ |
| 综合来看，建议方案 A | 我押 A，因为…；它可能在…处错 |
| 基于行业最佳实践 | 因为 <出处> 的 <事实>，所以…… |
| 这样可以吗？ | （先给出论证，再问那个非答不可的问题） |
| 高风险 / 优雅 / 能力强 | 说具体后果：这一撤，D-02.1 的前提没了 |
| 通过合理的架构设计 | 谁读什么、什么时候读、拿到什么；指不出就写"还指不出，因为…" |
| 已验证可行 | 证实了什么、推翻了什么、还剩什么没验证 |
| 未定项：待补充 | 一条一行，每条后面写"什么事实能解开" |
| 不是…而是… | **写成「是…」**：「这不是聪明，而是运气」→「这是运气」 |
| 不要… | **写成「禁止…」**：祈使句用「禁止」 |

## 二、九条硬规则

1. **结论写成可被反驳的命题**，禁止形容词串（"优雅、可扩展"）。
2. **比喻换成机制**；黑话、自造词、以及**本方法自己的行话**（核心／检验条件／未定项／收敛／接缝／落机制）要么换成平实说法，要么进 `glossary.md` 给一句人话定义。用久了不等于它不算黑话。
3. **一轮只给一个正在成形的想法命名**；名字用日常语言，要能解释自己。
4. **从常用词里借一个词当概念，必须当场声明差在哪**：写出"这个词平时指什么／在这棵树里指什么／差在哪"。`成本`、`密度`、`命中`、`优质`、`核心` 都属这类——用户以为是你说的那个意思，其实是你定的那个意思，**同名不同义就是误解的来源**。写不出"差在哪"，就换一个不像常用词的词，或加限定语（"可计费命中"）。借来的外部词（transformer、缓存命中）首次出现同样写清"它在这个项目里指什么"。
5. **没有前提或没有结论的句子删掉**——套话就是劣质 token。
6. **用户改写任何词**：全局替换，旧名记进 `glossary.md` 的「曾用名」，以用户的措辞为准。
7. 事实要么有出处（文件+行号／链接／命令与输出），要么写明"没查"。**假设禁止单独支撑结论**（写 `type: 假设` 并说明怎么验证）。
8. **给概念一个能算的说法，并把算式里的每个量讲完**：写法如"信息密度 = 起引导作用的 token ÷ 全部 token"。每个量在同一处交代四件事——**它在系统里指什么／从哪观测到（谁看得见它）／单位或量级／怎么数**；给不出"怎么数"的，标「候选（待答）」并写我在押哪个值。**禁止只给符号，禁止留空**——符号没解释，等于没给说法。数字出现在它改变判断的地方，别处给量级或留白。
9. **编号自带进度坐标**：需求线 `R-01`、事实 `F-001`、问题 `Q-03.1`、结论 `D-03.1`、判据 `K-01`、方案 `O-01`——点号在前，一眼看出属于哪个节点。

## 三、怎么提问

**把张力摊开**：这两条不能同时成立，你放弃哪一条、为什么——用户的**理由**才是推演的内容。再写出"我押哪条、我可能错在哪"。

**禁止给"2–4 个选项 + 我的倾向"**：实测里用户九次原样采纳了我的倾向，讨论就变成我给现成方案、用户盖章。用户自己写答案，这棵树才长东西；他给出的内容落在我的框架外，先回答一句"我的问题错在哪"。

**一次问一个**；能自己查的（文件、代码、网页）不问用户；只问用户拥有的东西——目标、取舍、可接受的代价、用词偏好。**每个问题都该是"非他不能答的取舍"**。

**禁止做用户体验调查。** 用户是需求与判断的提供者。禁止问"你以前用过什么、感觉怎么样"，禁止把讨论做成满意度问卷。他的**过往体验一律不写进 `facts.md`**。

**想谈现有系统，去查它**：源码、文档、日志、实测——进 `facts.md`，节点里写"这条事实让哪条结论变成什么"。**问不到人就继续往下推**：需要他判断而问不到的，给**候选**并标「（待答）」（例：`候选：token 花费 = 核心（待答）`）。

## 四、写给人读

**读者不是本行技术人**——`seed.md` 的 `reader:` 写了别的定位，就照那个来。技术词可以出现，但第一次出现必须当场落地：它是什么、拿什么例子能认出来、它在别处指什么而这里指什么。

**降低门槛靠解释，不靠模糊。** "你可以理解为……"后面如果什么都没解释，这句是空的；打比方不算解释，跳过机制不算通俗。**宁可直接说清楚，也不要用模糊词替掉专有词**——"大概是某种调度"比不说更坏。

**自检：这个词，用户不懂时会不得不问第二次吗？** 会 → 当场解释，不要等他问。他问了第二次，是这个概念没解释清，不是他读得慢。
