# 数据流推演

方法主干在 `SKILL.md`。这份文件管四件事：图怎么画、四问怎么走、缺口怎么收、偏在哪。

## 一、三张表加一节

记文本，不画图。状态 `S-`、动作 `A-`、缺口 `G-`，最后加一节「走一遍」。

状态写三样：编号、名字、用户在上面看见什么。

```
S-00 启动：用户看见列表页，列表为空
S-01 输入中：用户看见输入框里有字，列表还在
```

动作分用户动作与系统动作，都写六格。用户动作：

```
A-01 用户点「新建」：S-00 → S-01；读：无；写：一条空记录；看见：输入框获得焦点；失败：本地存储不可用 → 提示并停在 S-00
```

系统动作必须写触发来源：

```
A-02 自动保存（由 A-03 输入停顿 1 秒触发）：S-01 → S-01；读：输入框内容；写：本地存储；看见：右下角「已保存」；失败：同 A-01
```

六格不许省：谁在什么状态做什么 / 从哪个状态到哪个状态 / 读什么 / 写什么 / 用户看见什么 / 失败从哪退出。失败格写不出，说明缺一个状态，不是缺一句话。

缺口一条一行：先写缺什么，再写什么事实或哪个动作能补。

```
G-01 记录存在哪：查本地存储的容量上限后定
G-02 多设备同步要不要：暂不做，写进边界
```

解决掉的缺口删掉，图上只放活的。

## 二、场景卡

五格填满，写不满就是这条线还没成形。

| 格 | 写什么 | 反例 |
|---|---|---|
| 谁 | 具体的人，不是「用户」 | 用户 |
| 什么情况下 | 具体时间地点与触发 | 有需求的时候 |
| 想达成什么 | 他要在世界里改变什么 | 提升效率 |
| 现在怎么做 | 现在的替代动作 | 没法做 |
| 成功时看见什么 | 界面上可见的结果 | 体验好 |

场景必须是具体的。出现「一般用户会」这句，回到这一格重写。

## 三、主链与支撑线

主链选哪条：用户最常用、最痛、或者不做就白做的那个场景。写清放弃什么、代价是什么。

支撑线最多三条。每条也要有动作链。写不出动作链的进非目标。

主链恰好一条。出现第二条「主链」，说明在拿两个目标打架，先选一条。

## 四、四问

以一条动作为单位，逐条走，一问不跳。四问背后问的是同一件事：这一格靠什么存在。

1. **谁在什么状态做什么**：触发条件与前置状态。前置状态不存在，这条动作就是空的。
2. **读写什么**：数据从哪来、写到哪去。写下的数据后面谁读；没人读的写入就是多余的。
3. **用户看见什么**：反馈。看不见结果的动作为什么还要存在，得说清。
4. **失败从哪退**：错误状态、退出路径、用户看到什么。失败格空着，这条动作没写完。

四问走完，动作要么成立，要么变成缺口。

## 五、从动作推功能

功能从动作链里生，不从技术分层里生。

- 一个动作需要的功能，等于完成它需要的输入、状态、输出、失败处理。
- 一个功能指不到任何动作，不建。
- 同一份数据被两个以上动作读写，才值得抽成一个模块；只有一个使用者，就是一段代码。
- 顺序按动作：动作 1 的功能做完再做动作 2。不先做「登录系统」「数据层」「配置中心」。

## 六、走一遍

时间视角。概念第一次成形时写一次：拿一条具体输入，从起点动作走到终点，每步写谁、看见什么、系统改了什么。

禁止用抽象名词串代替。写不出「走一遍」，说明图还停在印象里。

四问是格子视角，走一遍是时间视角。两样都写，用户才拼得出整幅图。

## 七、收敛

三条都到才算推完：

1. 主链闭环：每个状态有写者，每条动作有出口，每个用户看见的结果有来源。
2. 缺口清零，或者每条都写着「不可解＋解锁条件」。
3. 没有新概念：新出现的东西能被已有动作解释；解释不了，先当缺口。

闭环四查，收工前跑一遍：

- 有没有状态没人写，凭空出现？
- 有没有动作没有失败出口？
- 有没有用户看见的东西指不到来源？
- 有没有系统动作挂不到用户动作链上，成了孤儿？

缺口只增不减就是铺摊子。停下来说明卡在哪一条，不接着往下堆。

推不动、需求不可行也是合法结局。写清哪条做不到、代价是什么，省下的实现成本就是成果。

## 八、一个正例

主链：场景「下班路上想起要买的东西，掏出手机记一笔」；起点动作「点输入框」；终点「看见列表里多了一条」；放弃「分类与标签」；代价「东西多了只能靠搜索找」。

flow 片段：

```
S-00 列表页 · A-01 点输入框 → S-01（输入中）
S-01 输入中 · A-02 点「存」→ S-00（列表多一条）；读：输入框；写：内存列表；看见：新条目出现；失败：空内容 → 抖动提示，停在 S-01
G-01 记录存哪：查本地存储容量后定
```

调研：先查同生态插件市场有没有「快速记录」类工具；匹配高、痛点低就先试用，否则自研。

切片：0 列表页＋输入框＋「存」按钮的骨架；1 输入能存进内存并显示；2 持久化；3 搜索。每片跑一遍，差什么回图上。

## 九、偏离的形状

| 形状 | 怎么发生的 | 防法 |
|---|---|---|
| 先画全景图 | 一开始就想把整个系统画完 | 只画当前主链碰到的格子，没碰到的标「未画」，不留空 |
| 自造需求名目 | 把用户的话换成「信息层」「调度器」这类自造词 | 需求线里只放用户说的动作和场景 |
| 脱离场景 | 开始谈「一般用户会……」 | 每条线回到场景卡，填不满就不推 |
| 预设架构 | 开口就是「前后端分离」「插件系统」 | 架构是动作链的后果，先画动作再谈结构 |
| 动作没有失败出口 | 只写成功路径 | 每条动作必须写失败格，写不出就是缺状态 |
| 缺口只增不减 | 每个动作都长出新问题，还都当成绩 | 一次推进一个缺口；解决不了标「不可解＋解锁条件」 |
| 调研当推演 | 把查到的项目直接当结论 | 调研给候选与证据，主意链自己推 |
| 把演示当验证 | 跑通一次就写「验证可行」 | 写清它证实了什么、没证实什么、还剩什么 |
| 抽象没有第二个使用者 | 先建「核心层」再找用途 | 抽象有第二个动作使用时才建 |
| 切片按技术层切 | 先做数据层、认证、配置 | 切片顺序等于用户动作顺序 |
| 边界写成愿望 | 「不做复杂功能」 | 写清不做什么、做不到什么、只适配什么场景 |
| 结论是形容词 | 「体验流畅」 | 写成可被反驳的：从点输入到看见列表不超过两次点击 |
| 图只长不闭环 | 状态越画越多，没人写，也没人读 | 每次收工跑闭环四查 |
