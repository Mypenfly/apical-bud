# S2–S3：推演（先摆候选，再定结论）

> **落盘时机**：本阶段谈定的任何内容，都先在对话里说清楚、拿到你的答复，再写进文件。**提案不落盘**——文件是留痕，不是介质。

目标：把 S1 认领下来的每一项，**先摊开成几条不能同时成立的候选，再挑出站得住的那一条**。

**推演分两跳，两跳各做一次"摊开—挑一个"：**

| | 从哪儿出发 | 摊开成什么 | 挑出什么 |
|---|---|---|---|
| **第一跳**（S2） | S1 认领下来的每一项 | 这项需求"到底指什么"的几种互不相容的读法 | **需求定稿** `concept/need.md` |
| **第二跳**（S3） | 需求定稿 | 几种互不相容的理念候选（这一屏是什么气质） | **顶芽** `concept/concept.md` |

两跳都要做，**不许跳过第一跳直接想理念**。跳过第一跳，摊开的就还是我知识库里的现成方案，不是你的需求。

> **与 S3 的分工**：这里推出来的是**主张**（要做到什么、为什么）。**别在这里给理念起名**——名字是第二跳收拢的产物；也别把机制写成理念（"挑现成的、可配置"是机制，不是气质）。

## 一个节点两档：候选 / 定论

节点文件 `derivation/N-00N-<slug>.md`，frontmatter 用 `kind:` 分两档，门禁分别检查：

| | `kind: 候选` | `kind: 定论` |
|---|---|---|
| 回答什么 | 这一项**可以**是什么样 | **为什么是它** |
| `from:`（必填） | 指向层、`need`、或另一个节点 | 同左 |
| `stage:` | `S2`（第一跳）或 `S3`（第二跳） | 同左 |
| `## 推演` | **不要求**（还没有推理链，这正是它叫候选的原因） | **必填**：因为 <父的判据 / 用户的认领> → 所以 <这个主张> |
| `## 反例` | 不要求 | 必填（什么情况下它不成立） |
| `## 对立面` | **必填**：它和哪一条不能同时成立 | —— |
| `## 放弃了什么` | **必填**：要了它，就得放弃什么 | —— |
| `## 淘汰理由` + `## 复活条件` | `status: dropped` 时必填 | 同左 |
| 祖先链 | 只到 `from` | 必须一路走到种子 |

`status: kept`（留着）/ `dropped`（淘汰）。**淘汰的节点不删**：它是树上被剪掉的枝，半年后是"为什么不选另一条路"的唯一答案。

## 摆候选的四条规矩

1. **成对出现。** 每条候选的 `## 对立面` 必须指向另一条真实存在的候选，**那一条也要指回来**。门禁检查这个来回。找不到对立面的，不是候选，是结论——直接按 `kind: 定论` 写。
2. **每条都写"放弃了什么"。** 一条候选如果什么都不要放弃，说明它没说到取舍，还停在形容词。
3. **说人话，能被否。** 判断标准：用户能不能说"这条我不要，因为……"。写成一串形容词（"优雅、现代、可扩展"）的候选，用户无从否起。
4. **对照着用户的原话写。** 候选最好直接引用种子或 `## 拆词与认领` 里的原话，让用户一眼看出这是他的哪句话在分岔。

**数量由内容决定，不由轮次决定。** 一个项摊出两条互相对立的就够；硬凑成五条只会稀释。**但没有对立面的候选不算数**——这一条是硬的。

## 定论的两条规矩

1. **定论必须从候选里挑**，或在候选之外补一条**并写清为什么现有的几条都不行**（补的那条要写 `## 淘汰理由` 式的说明，不能默默加进来）。
2. **淘汰是有条件的判断**："因为 <当时的推断或判据>，所以现在不选它"，并附一行**复活条件**（什么情况出现就该把它捡回来）。**推断变了，淘汰结论就作废**，回这一步重判。

## 第一跳：需求定稿（S2 的产物）

把第一跳的定论合起来，写成 `concept/need.md`：

- `status: settled`；
- `## 定稿`：一句话（≤120 字）——**用户能指着它说"对，我要的就是这个"**；
- `## 每一项来自哪一条`：逐条列出"定稿里的哪个成分 ← `N-00N`"，门禁要求覆盖第一跳全部 `kept` 的定论节点。

**这一句话是第二跳唯一的出发点**，也是"用户更理解了自己的需求"这件事唯一的证据。写不出这句、或写出来用户不认，都说明第一跳没做完。

## 第二跳：理念概念（S3 的产物）

从需求定稿的每一条成分出发，摊开理念候选，收拢出一个——**要求见 `apical.md`**。

## 生长顺序

**一轮只做一个动作：摊开一次，或挑一个。** 不要一边摊一边挑。

1. 挑一个还没摊开的项（通常从最靠近种子、或用户认领为`核心`的那一项开始）。
2. **摊开**：写 2 条以上互相对立的候选，每条带 `## 对立面` 与 `## 放弃了什么`，说在对话里给用户看。
3. **问用户**：这些候选里哪几条"一看就不是我要的"，为什么。用户的回答会砍掉一批，也会补出我没有的候选。
4. **挑一个**：写 `kind: 定论` 节点，带完整推演链与反例。落选的标 `dropped` + 淘汰理由 + 复活条件。
5. 移到下一项。**同一项还有没解决的对立面，就不许写定论。**

门禁要求：**每一项都要有下文**（至少一条候选），且两跳各至少有一次摊开。

## 一条推演依赖"程序怎么表现"时：三选一（当轮必做）

推演与淘汰太容易建立在一个**我没读过的事实**上（"它必然要用 niri"、"它不可能被暂停"）。这类句子一旦写成机制，就会拿去筛掉本来能用的候选。所以当轮必须选一条，并写进节点：

| 出口 | 什么时候走 | 落盘要求 |
|---|---|---|
| **① 读源码/文档/日志** | 盘上有源码或文档 | 写出**文件 + 行号或函数名**；写不出就是没读 |
| **② 承认没读** | 读了也没有定论 | 明写"我没读 X"，把它降级为反例或未验证假设（`evidence: E3`）；**不许再拿它当硬要求** |
| **③ 交给用户做实验** | ①②穷尽后仍必须真机实测 | 交接三件套（见下），并在 `tech/probes/` 记一条待验证 |

**判断标准是"读一次得到答案吗"**：能，就不许让用户重启机器。**禁止把 ① 该做的事推给 ③。**

### 交接三件套（缺一不可）

1. **交接文档** `tech/handoff-<主题>.md`：为什么必须实测 · 具体步骤 · **通过了算过 / 不通过该怎么办** · 回滚步骤 · 要收哪些日志；
2. **一段可直接复制的提示词**（写在交接文档里）：用户拿去在标准模式新会话里粘贴，自包含，**不读讨论对话也能执行**；
3. **回报格式**：结果写 `tech/probes/<id>-result-<日期>.md`，原始日志放 `tech/probes/evidence/`。

拿到结果后：先判断它**推翻了哪一条**（可能是机制命题、可能是判据），把结论落到对应文档，并在轮次纪要里记一笔。**实验是取证，不是实现**——不写生产代码。

## 清单要诚实：别把"我想到的"说成"只有这些"

给候选、给路径、给选项时（拆出来的构成项、摊开的候选、三选一里的三条路、`tech/options.md` 里的候选都算）必须写一行 **`清单来源:`**：

- 这份清单是从哪儿数的（本机现状 / 源码里的入口 / 某个包的仓库 / 推论）；
- **我查了哪些、没查哪些**，"因此可能漏掉什么"。

反模式：**假穷尽**——"这一屏由谁画只有三条路"。如果其中两条是排查出来的、一条是推出来的，那不是空间只有三条，而是**你只看了三个地方**。把这句话换成盘点，用户才有得比较。

## 什么时候该停下来回退

| 症状 | 说明 | 动作 |
|---|---|---|
| 某项摊不出两条对立的候选 | 这一项的判据可能自相矛盾，或者它不该在这一层 | 回 S1 拆词或合并层 |
| 摊出来的候选必须引入一套新机制才能自洽 | 它其实是一个**新的理念候选**，不是需求这一跳的候选 | 允许，但要挂到它真正的父层上，并在第二跳里参加竞争 |
| 两项的候选互相要求对方 | 循环依赖 = 拆词切错 | 回 S1 重新拆 |
| 需求定稿写出来用户不认 | 第一跳没做完，或种子那句话本身站不住 | 先回第一跳补候选；种子错了就回 S0，把旧版挪进「被否的表述」 |

**推演失败是正当产出**：写进 `audit/verdict.md`（`V-00N`，结论"转向"或"终止"），明确告诉用户。硬造一个概念把树撑起来，比承认推不动更贵。

## 一个完整的例子

种子的 statement：*"让长时间读代码的人眼睛不累、注意力不被打断"*

**S1 拆词与认领**（写进 `seed/real-need.md`）：

| 词 | 我拆的构成项 | 用户认领 |
|---|---|---|
| 不累 | 亮度刺眼 / 字太小 / 颜色太花 / 看久了干涩 | 颜色太花 = 核心；亮度刺眼 = 次要；其余不算 |
| 不被打断 | 弹窗 / 动效 / 装饰抢眼 / 通知 | 装饰抢眼 = 核心；动效 = 次要；其余不算 |

**第一跳（S2）**——拿"颜色太花"这一项摊开：

- `N-001`（候选，`from: [L-001]`，`对立面: N-002`）：颜色少，就是把饱和度压低。
  `## 放弃了什么`：放弃了用颜色区分层级的能力。
- `N-002`（候选，`from: [L-001]`，`对立面: N-001`）：颜色少，是**只保留承载信息的那一种颜色**，其余用字重和留白区分。
  `## 放弃了什么`：放弃了"多色体系"这种一眼分类的便利。
- 问用户：这两条哪条不是你要的？用户答："第二条。但我不想连字重都变，字重一多也乱。"
- `N-003`（定论，`from: [L-001]`，`kind: 定论`）：界面里的颜色只用来承载信息，层级靠留白，不靠字重也不靠色块。
  `## 反例`：完全没有层级提示时，定位成本上升——所以留白必须真的拉得开。
  → `N-002` 标 `dropped`，淘汰理由"用户否掉了字重方案"，复活条件"若发现纯留白在小屏上分不出层级"。

需求定稿（`concept/need.md`）：**"看久了不觉得花，也不觉得乱；眼睛不用在颜色和粗细上做判断。"**

**第二跳（S3）**——从定稿出发再摊一次，收拢出理念名（`纸墨`），机制（"低字面对比要够、装饰即干扰"）落到侧枝的 `M-`，供选型阶段当限制条件用。注意 `N-001` 没有消失：它留在树上，是"为什么不是低饱和配色"的答案。

## S2 出口条件（门禁）

- 第一跳有 ≥1 条 `kind: 候选` 节点（`stage: S2`），每条有 `## 对立面` 与 `## 放弃了什么`，且 `## 对立面` 指向的节点也指回来；
- 第一跳有 ≥1 条 `kind: 定论` 节点（`stage: S2`），带 `## 推演` 与 `## 反例`；
- `concept/need.md` 存在，`status: settled`，`## 定稿` 非空，`## 每一项来自哪一条` 覆盖第一跳全部 `kept` 定论节点；
- 每个 `L-` 层都有节点挂上去；
- 所有 `kept` 节点的祖先链都能走到种子（无孤儿节点）；
- 依赖"程序怎么表现"的推演走过了三选一（读源码的写出处、没读的写明、要实测的进 `tech/probes/`）；
- 没有阻塞 S2 的未决问题。

## S3 出口条件（门禁摘录）

- 第二跳有 ≥1 条 `kind: 候选` 节点（`stage: S3`），规矩同第一跳；
- 每条第二跳节点都能沿 `from` 走到 `need`，再走到种子；
- `concept/concept.md` 的全部要求见 `apical.md`。
